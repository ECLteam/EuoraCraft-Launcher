1. 执行摘要

本次审计覆盖了后端 ECL/（异步服务、下载器、账号鉴权、游戏核心、连接器）、ECL/api/ IPC 层、以及 frontend/src/ 前端（Vue 3 + 插件 SDK）。整体架构清晰、分层合理，异步化改造（Microsoft 认证）方向正确。主要风险集中在：

  • 并发/线程锁：多处「同步方法里触发无跟踪的 asyncio 任务」与「持锁做 I/O」反模式。
  • 异常静默：账号加载、安装器等关键路径存在裸 except: pass，可能吞掉真实故障。
  • 安全：插件 SDK 存在动态脚本执行（new Function / <script> 注入）；game_args/jvm_args 透传欠缺强校验。
  • 资源&生命周期：下载器停止不等待、账号管理器关闭不追踪异步任务，关闭链不彻底。

严重级别判定标准

级别含义
高可能导致崩溃、数据丢失、安全风险、事件循环阻塞、功能不可用
中边缘场景下出错、资源泄漏风险、错误被掩盖、体验受影响
低代码风格、可读性、潜在边界问题，可择机优化

2. 并发与线程锁（重点，共 12 项）

这是项目中风险最集中的领域。后端已部分完成「异步化」改造，但仍有同步/异步交叉使用造成的锁与任务管理隐患。

高 DynamicSemaphore 在同步方法里触发异步任务，且不跟踪任务句柄 ECL/game/Core/Downloader.py:41-63

`release()` / `change()` 是同步方法，却 `asyncio.create_task(_release())` / `create_task(_change())`，任务不被保存、不被取消。

为什么要改： ① 若调用发生在事件循环之外（如线程数据流回调），`asyncio.Condition` 可能报 RuntimeError: got a new event loop 或调度异常； ② fire-and-forget 任务在关闭/取消时可能丢失，导致信号量许可证泄漏，下载队列被永久卡住； ③ `change()` 缩短时未通知阻塞等待者让其重新计数，可能与实际并发不符。
def release(self):
    async def _release():
        async with self._condition:
            self._value += 1
            self._condition.notify()
    asyncio.create_task(_release())   # ← 不 await、不保存 task

def change(self, new_value):
    async def _change():
        async with self._condition:
            delta = new_value - self._value
            ...
    asyncio.create_task(_change())    # ← 同上

建议：将二者改为 async def 并同步 await；若必须保留同步接口，则保存返回的 Task 到受跟踪集合（如 self._pending），于关闭时统一 cancel，并对已关闭的事件循环做好保护。

高 Downloader._put_event 以 fire-and-forget 方式投递事件 ECL/game/Core/Downloader.py:596

进度/速度事件通过 asyncio.create_task(...) 投递到队列，不保留任务引用。

为什么要改：下载中若应用关闭或事件循环停止，进度事件会静默丢失，前端进度条停摆；也增加了不可预期的任务残留。
中 ConnectorService._current_players 用 run_coroutine_threadsafe 跨线程跑协程 ECL/services/connector.py:214-217

同步方法序列化到事件循环去发起网络请求，依赖 `self._client.loop` 存活。

为什么要改：若事件循环已停、未运行、或从错误线程访问，会抛异常后静默回退到缓存数据，玩家列表可能过时却无感知。
中 InstancesManager._read_stream 线程内 proc.wait() 阻塞不及时移除实例 ECL/game/Core/InstancesManager.py:51-57

为什么要改：读者线程 `stream.close()` 后 `proc.wait()` 直到子进程退出才更新 `self.instances`，若游戏进程被卡住会导致实例状态长期悬挂，且无法被关停逻辑及时回收。

中 InstancesManager.shutdown_all 阻塞 sleep + 重复取锁 ECL/game/Core/InstancesManager.py:195-207

为什么要改：`time.sleep(0.1)` 阻塞关闭流程；清空实例先取锁、sleep、再取锁，若后台读者线程慢，关闭后 `self.instances` 可能仍残留。

中 Downloader 守护回调派发线程缺乏统一关闭跟踪 ECL/game/Core/Downloader.py:696-697

为什么要改：`_dispatcher_thread` 为 daemon 线程，异常退出或事件循环先停时，可能未等回调 flush 就结束进程，丢失最终回调。

低 密码/密钥/共享状态存在被多线程同时读写的并发面 ECL/services/accounts.py · plugin manager

为什么要改：账号等共享状态若在后台线程（下载、插件）与 IPC 协程间并发访问，缺锁可能产生竞态。建议复查所有「线程读 + 协程写」的共享容器。

低 多处理路径使用同一进程内部可变单例，未加防重入 ECL/api/bridge.py 等

为什么要改：IPC 命令若被前端并发触发（如快速连点），共享可变状态（下载字典、任务句柄）缺少幂等保护。

3. 异步与事件循环（共 8 项）

中 ApplicationContext.close 用 asyncio.run() 另起事件循环关异步资源 ECL/application.py:104
为什么要改：若资源的协程依赖当前正在运行的事件循环（如共享池、绑定的 async client），在另一个新循环里 asyncio.run() 会抛 RuntimeError 或导致关不掉。建议在启动时保存单例事件循环并提供 loop.call_soon_threadsafe 关闭或维护独立的关闭循环。
中 Downloader.stop() 调度 _safe_stop() 但不等待完成 ECL/game/Core/Downloader.py:797-815
为什么要改：stop() 调 pause 后仅 run_coroutine_threadsafe 排入 _safe_stop() 就返回；`aclose()` 与线程 join 是否完成无保证。调用方（GameService.close）随后可能立刻销毁上下文，产生竞态。
中 GameService.close 不等待下载协程完成、不显式关闭 AsyncClient ECL/services/game/base.py:320-324

已核验：关闭时逐个 `downloader.stop()`，但未 await 下载协程结束，也未直接 close downloader 内部的 `httpx.AsyncClient`。

为什么要改：应用退出时进行中的下载可能残留未关的异步客户端与线程，拖慢退出或触发资源泄漏告警。
中 AccountManager.close 对异步关闭不追踪任务、所有权不明确 ECL/services/accounts.py:1099-1111, 218-233
为什么要改：① `self.microsoft_manager` 既可能由外部传入（共享）也可能内部创建，无 `_owns` 标志，close 时可能误关外部共享管理器或漏关自建管理器；② 异步 `aclose()` 若依赖原事件循环，在 sync close 上下文执行可能失败。
中 ConnectorService 无显式 close/关闭生命周期 ECL/services/connector.py:35-75
为什么要改：房间状态、EasyTier 节点、异步/同步 client 混存，离开房间时部分清空，但缺集中关闭路径，退出时可能遗留网络资源。
低 Downloader.gg 事件收集/速度任务在 run() 关闭时异常被吞 ECL/game/Core/Downloader.py:739-757
为什么要改：取消事件收集、速度任务时无异常记录，排查关闭问题缺少线索。
低 Downloader._preflight 依赖 async with 上下文管理并发 HEAD 任务 ECL/game/Core/Downloader.py:275-283
为什么要改：asyncio.create_task 并发 HEAD 请求，靠 await gather 与 async with 兜底；个别任务异常未先捕获时清理顺序依赖实现，建议显式 gather(return_exceptions=True)。

4. 资源管理与生命周期（共 6 项）

高下载资源池缺少统一归属与显式回收GameService.base
为什么要改：下载器、API client 混在 _active_downloads 与 _GameState，关闭不彻底，长期运行或反复开关游戏可能累积客户端。
中网络连接池未集中共享/统一创建多处
为什么要改：账号、连接器、桥接各自 create client，建议在应用层建共享连接池，降低握手开销并便于统一超时/关闭。
中文件/临时产物缺少统一清理策略ECL_data/exports、.minecraft
为什么要改：导出、缓存目录可能随会话增长，建议提供定期清理或体积上限策略。
低部分线程（版本监听）生命周期靠 join 超时兜底base.py:318-319
为什么要改：join(timeout) 超时后不强制停线程，极端情况下残留。若能改用协程 + 取消信号更稳。

5. 异常处理（共 10 项）

高 MicrosoftAuth._load_accounts 裸 except: pass 吞掉账号加载故障 ECL/game/Core/MicrosoftAuth.py:626-627
为什么要改：损坏/不兼容的账号文件被静默忽略，用户的微软账号可能「凭空消失」且无任何提示，数据可恢复性差。
高 YggdrasilAuth._load_accounts 同样静默吞异常 ECL/game/Core/YggdrasilAuth.py:260-261
为什么要改：JSON/网络/存储异常一律吞掉，正版曲奇账号加载失败无感知。
高 LoaderInstaller.install_neoforged 将解析错误隐式降级为 Forge 安装 ECL/game/Core/LoaderInstaller.py:51-58
为什么要改：NeoForge 安装包畸形时静默回退到旧 Forge 路径，真实安装失败被伪装成回退行为，难以定位。
中 FilesChecker.download_asset_index 吞索引下载错误 ECL/game/Core/FilesChecker.py:112-118
为什么要改：资源索引缺失/损坏时返回空下载列表，可能造成资源下载静默遗漏。
中 NetLibs.get_forge_version 吞 404/网络错误 ECL/game/Core/NetLibs.py:383-388
为什么要改：Forge 安装器校验失败被忽略，下载列表不变却无告警。
中 YggdrasilAuth 删除账号前吞掉 invalidate 失败 ECL/game/Core/YggdrasilAuth.py:372-380
为什么要改：服务端会话吊销失败仍删本地数据，可能残留服务端登录态。
中 多处宽泛 except Exception 缺少诊断信息 MicrosoftAuth.py · connector.py · accounts.py · launch.py
为什么要改：网络/JSON/IO 错误被折叠成统一失败文案，排查成本高。建议在关键失败处补 logger.exception 或上下文标签。

6. 网络安全（共 4 项）

中 远程图片下载 verify=False 关闭 TLS 校验 ECL/api/bridge.py:194-199

已核验：`_download_remote_image` 用 httpx.AsyncClient(verify=False, ...)，有超时与大小上限。

为什么要改：关闭证书校验可被中间人注入图片。图片源若非完全可信，建议对可信域名启用 ssl 校验，或至少对不可信源做内容白名单/类型限制。
中 客户端未强校验 open_url 的 URL scheme frontend/src/utils/openExternal.ts:19
为什么要改：前端把原始 URL 直送后端 open_url，若后端校验不一致，可能打开 file:// 或自定义协议。建议前端按 scheme 白名单校验后再提交。
低 部分网络调用缺少显式重试包装 accounts.py · connector.py · files.py
为什么要改：临时性网络抖动以失败收场。对 GET 幂等接口可加有限重试 + 退避，提升体验。

7. 前端与插件安全（共 8 项）

前端通过插件 SDK 支持第三方插件渲染动态内容，这部分安全边界需重点把关。

高 evaluateVueScript 用 new Function 动态执行插件脚本 frontend/src/composables/usePluginBridge.ts:339
为什么要改：等价于任意代码执行。恶意或被入侵的插件可完全控制前端运行时。若无法避免，应限制在沙箱内并走严格审核的插件签名。
高 插件脚本以 <script> 追加方式执行 usePluginBridge.ts:296-300
为什么要改：动态注入脚本元素执行插件 JS，绕过模板静态限制；建议改用受控执行的 Web Worker/受限上下文。
中 插件 SDK innerHTML 注入未统一净化 plugin-sdk/dom.ts:84,196-204 · plugin-sdk/component.ts:48-49,150-158
为什么要改：插件 HTML 模板、列表项、CSS 直接写入 DOM。建议在 SDK 入口统一经 DOMPurify 白名单净化后再注入。
中 插件初始化用 Promise.all().catch(()=>{}) 静默吞错 usePluginBridge.ts:660-679
为什么要改：任一路径失败都会丢弃整个初始化结果，用户看到残缺插件 UI 而后端日志被隐藏。

8. IPC 与输入校验（共 6 项）

高 game_launch 的 game_args / jvm_args 透传且未强校验 ECL/api/game.py:386-420

`LaunchRequest` 校验后 `model_dump()` 再以 `**values` 展开传给 `launch_instance(...)`；quick_target 时合并前端提供的 game_args 与内部 quick 参数。

中 debug_process_spawn 未严格校验进程名/类型 ECL/api/bridge.py:627-649
为什么要改：虽受 debug 门控，仍应对 name/type/args 做白名单，防止误用为任意子进程启动口。
低 事件 unlisten 错误被静默忽略 frontend/src/api/client.ts:150-156
为什么要改：清理失败被隐藏，难以发现监听泄漏。
低 settings_get 的 config.list() 未传 section，依赖后端默认 frontend/src/api/client.ts:275
